# Windows云端字体验证报告

## 结论与范围

使用GitHub Actions `windows-2022`、镜像`20261112.366.7`和LibreOffice 25.2.3.2，完成学校原字体PDF导出。成功运行：[43541893783](https://github.com/zc0429/graduation-project/actions/runs/43541893783)，源提交`d117e1989b05921263f61d514b1b7456ff0d1d9b`。

**通过：PDF可编辑文字实际使用SimSun、SimHei、Times New Roman；所用字体全部嵌入并子集化；页码实际使用9pt SimSun。** 该结论来自PDF字体对象、嵌入字体内部名称、实际文本span及独立Poppler检查，不是只读DOCX字体名称。

未验证：Microsoft Word重新排版、纸质打印，以及既有栅格图和历史截图内部的原字体。当前正式PDF不再是Noto替代字体预览。没有把图片内的UI字体或旧图字形也标为全部符合三种字体。

## 字体来源、真实性与使用范围

|字体|实际版本|来源与处理|PDF实际使用|
|---|---|---|---|
|宋体 SimSun|5.24|Windows云端镜像原有`simsun.ttc`，内部名称含SimSun/宋体；同集合中的NSimSun另外记录，没有作为目标字体冒用|3363个文本span，包含94个页码|
|黑体 SimHei|5.03|初始缺失；通过微软官方简体中文补充字体组件安装`simhei.ttf`，无需重启|250个文本span|
|Times New Roman|7.02|Windows镜像原有常规、粗体、斜体、粗斜体四个字体文件|2799个文本span，实际PDF使用常规及粗体|

实际文件名、内部family、版本、SHA-256和OS/2 `fsType`保存在[初始清单](../thesis-windows-fonts-43541893783-1/font-inventory-initial.json)及[安装后清单](../thesis-windows-fonts-43541893783-1/font-inventory.json)。SimHei安装记录见[官方组件日志](../thesis-windows-fonts-43541893783-1/windows-optional-fonts.log)。目标文件的`fsType=8`，未设置禁止子集化位；最终PDF各字体对象均为嵌入子集，并可读取其内部字体family。

微软官方[语言按需功能说明](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/features-on-demand-language-fod)列出了`Language.Fonts.Hans~~~und-HANS~0.0.1.0`。[字体FAQ](https://learn.microsoft.com/en-us/typography/fonts/font-faq)区分了字体独立再分发与按字体嵌入权限进行文档嵌入。相关页面摘录见[官方来源记录](official-font-sources.json)。

本轮只在提供这些系统字体的Windows主机上渲染，未将字体文件复制到Linux、放入Git或作为独立文件上传。取回Linux的是合法文档嵌入形式的PDF及文档/校样/元数据，用于阅读和检查；没有从PDF提取字体再安装使用。未下载来源不明或许可不清的第三方宋体/黑体包。Windows方案已成功，无需启用Linux替代成品。

第二轮说明：仅把页码域运行和段落标记指定为宋体仍不够。LibreOffice更新动态PAGE字段时取用了继承Normal的Footer样式字体；本轮将Footer样式的各字体槽也明确设为9pt宋体，并清除继承首行缩进，使实际PDF页码正确。没有把验收条件改成允许Times New Roman页码。

## 验证证据

1. Windows字体清单读取实际文件内部名称，而非只检查文件是否存在。官方组件安装后再次核验，三种字体均存在。
2. [PDF字体报告](../thesis-windows-fonts-43541893783-1/actual-pdf-fonts.json)逐个读取嵌入字体元数据，确认8个TrueType子集对象属于三种目标family；实际使用片段合计6412个，无未知字体、中文字体错误、英数字体错误或页码字体错误。8是子集对象数，不是8种字体。
3. [页码记录](../thesis-windows-fonts-43541893783-1/font-layout-check.json)核对摘要I/II及正文1—92的全部94页，均为9pt SimSun。题目18pt、115个标题、335个普通段落、275行代码及三个页脚部件按既有规范核对；Footer语义样式增加明确检查。
4. [文档检查](../thesis-windows-fonts-43541893783-1/document-check.json)确认A4和既定页边距，九章真实分页、三页横向业务图、120目录目标、所有表格文字、31段代码和112项题注/文献条目完整，文字物理页边界0处越界。只做重排后必要完整性校验，不重复系统内容审计。
5. 取回成品后验证Actions ZIP摘要及DOCX/PDF SHA-256；独立使用[Poppler](independent-pdffonts.txt)与[MuPDF/FontTools](independent-pdf-fonts.json)复查，结果一致。旧的94项页码错误候选仍被新检查器拒绝，且失败时PDF句柄已释放，见[负对照结果](negative-control-result.json)。旧Linux替代预览也被拒绝为原字体，见[负对照摘要](negative-control-summary.json)（原始JSON无损压缩保留，解压SHA-256已核对）。
6. 实际查看101页对应的26张Windows四页校样，另放大第1、10、59、60、72、98页。未发现新增乱码、裁切、重叠或异常近空白页；常规续表、代码自然跨页和章末留白保留。逐页记录见[visual-review.csv](visual-review.csv)。

旧论文正文、学校模板和图像原件不变；DOCX仅因字体/页脚样式及重新生成产生差异。正文仍为九章87页，PDF全本101页，未为追页数增加或删改内容。本轮不运行系统测试或GLM实验，不产生新的系统通过率。

## 保留的限制

- Microsoft Word引擎与实物打印未验证；本轮原字体成品明确由Windows LibreOffice生成。按本次用户允许的云端LibreOffice方案交付，不再要求用户本机完成导出。
- 28幅既有栅格图和历史截图的内部字形不在PDF可编辑文字字体验证范围内，图题及图外正文属于已核验文字。为保护历史证据没有改图或伪造图内字体元数据。
- DOCX在其他环境重新排版时仍取决于该环境字体与引擎；本轮PDF已经嵌入字体，阅读无需本机另装宋体、黑体或Times New Roman。后续修订可继续由云端流程生成。
